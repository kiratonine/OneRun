# План разработки — БЭКЕНД 2 (модуль отчёта и LLM)

**Проект:** «Сводный рейс» — консолидация грузов в отдалённые посёлки Мангистау
**Роль:** модуль генерации отчёта, интеграция с Gemini, режим заглушки
**Бюджет времени:** ~3–4 часа, разбитые на независимые блоки
**Ветка:** `feat/backend-report` (от `base`)

Задача подобрана под ограниченное время: это **изолированный модуль**, который не блокирует никого и не зависит ни от чьего кода. Ты можешь начать в любой момент после появления ветки `base` и делать блоки в любом порядке.

---

## 1. Зона ответственности

Ты владеешь ровно этой папкой и ничем больше:

```
backend/src/report/
├── report.module.ts
├── report.service.ts
├── dto/trip-summary.dto.ts
├── llm/
│   ├── llm.provider.ts        # интерфейс
│   ├── gemini.provider.ts
│   └── mock.provider.ts
├── prompts/
│   └── report.prompt.ts
└── templates/
    └── fallback-report.ts
```

Ты **не трогаешь** ничего за пределами `backend/src/report/`. Ни `app.module.ts`, ни `trips`, ни `frontend/`. Модуль уже подключён бэкендом-1 в первом часу — тебе остаётся заменить содержимое двух файлов и добавить свои.

Это и есть гарантия чистого merge: ваши изменения не пересекаются ни в одной строке.

**Одно исключение:** переменные окружения. Свои строки для `.env.example` не добавляй сам — отправь их бэкенду-1 текстом, он впишет. Иначе получите конфликт в единственном общем файле.

## 3. Контракт — вход и выход

**Не менять без согласования.** Бэкенд-1 заполняет вход, фронтенд рендерит выход.

```ts
// dto/trip-summary.dto.ts

export interface TripSummaryOrderDto {
  code: string;              // 'ORD-003'
  shipperName: string;       // 'ИП Әулет'
  toName: string;            // 'Шетпе'
  cargoName: string;         // 'Стройматериалы'
  weightKg: number;
  boxesCount: number | null;
  boxNote: string | null;    // '10 мешков по 20 кг, 60×40×40'
  dropIndex: number;         // 1 = выгружается первым
  loadPosition: number;      // 1 = грузится последним, у дверей
  priceKzt: number;
  legDistanceKm: number;
}

export interface TripSummaryDto {
  tripCode: string;
  hubName: string;           // 'Актау'
  stopOrder: string[];       // ['Актау','Акшукур','Шетпе','Бейнеу','Актау']
  totalDistanceKm: number;
  soloDistanceKm: number;
  savedDistanceKm: number;
  savedCostKzt: number;
  totalWeightKg: number;
  costPerKmKzt: number;
  orders: TripSummaryOrderDto[];
}

export interface ReportResult {
  contentMd: string;               // Markdown, идёт на фронт как есть
  raw: unknown | null;             // сырой ответ провайдера, для отладки
  source: 'gemini' | 'mock';
}
```

Единственный публичный метод:

```ts
generate(summary: TripSummaryDto): Promise<ReportResult>
```

**Метод не бросает исключений никогда.** Любая ошибка внутри — это молчаливый откат на заглушку. Падение чужого API не должно ронять демо на сцене.

## 4. Переменные окружения

```dotenv
# Режим генерации отчёта: gemini | mock
LLM_PROVIDER=mock
GEMINI_API_KEY=
GEMINI_MODEL=gemini-2.5-flash
```

Логика выбора провайдера — три условия, именно в таком порядке:

1. `LLM_PROVIDER` отсутствует или равен `mock` — заглушка
2. `LLM_PROVIDER=gemini`, но `GEMINI_API_KEY` пустой — заглушка, с предупреждением в лог
3. `LLM_PROVIDER=gemini` и ключ на месте — Gemini, а при любой ошибке — тихий откат на заглушку

Так вы можете разрабатывать и тестировать весь день без единого запроса наружу, а ключ подключить последним действием перед сдачей. И если квота кончится на питче, продукт этого не заметит.

## 5. Блоки работы

Блоки независимы. Делай в любом порядке, в любые окна времени.

### Блок 1 · Заглушка и шаблон отчёта — ~50 минут

Самый важный блок. После него проект уже полностью работоспособен, и всё остальное — улучшение.

Пишешь `templates/fallback-report.ts` — чистую функцию, которая собирает Markdown из `TripSummaryDto` без всякого LLM:

```ts
export function buildFallbackReport(summary: TripSummaryDto): string {
  // Markdown-строка из данных summary
}
```

Структура отчёта:

1. **Заголовок** — код рейса, дата
2. **Маршрут следования** — нумерованный список из `stopOrder` с километражом
3. **План погрузки** — таблица, отсортированная по `loadPosition` по убыванию (то есть в порядке фактической загрузки в прицеп): заявка, посёлок, груз, вес, места, где размещать
4. **Стоимость по заявкам** — таблица: заявка, отправитель, посёлок, вес, км, цена; строка «Итого»
5. **Экономический эффект** — было `soloDistanceKm`, стало `totalDistanceKm`, сэкономлено `savedDistanceKm` км и `savedCostKzt` тенге

Правило размещения формулируется словами: груз, который выгружается первым, ставится ближе всего к дверям; груз последней точки уходит в глубину прицепа. Для каждой позиции — обоснование в одну строку вида «выгружается первым, в Акшукуре — ставить у дверей».

`mock.provider.ts` просто оборачивает эту функцию в интерфейс провайдера и возвращает `source: 'mock'`.

**Готово, когда:** `POST /api/trips` возвращает читаемый, полный, осмысленный отчёт без единого внешнего запроса.

### Блок 2 · Интеграция с Gemini — ~70 минут

`llm/llm.provider.ts` — интерфейс:

```ts
export interface LlmProvider {
  generate(summary: TripSummaryDto): Promise<ReportResult>;
}
```

`llm/gemini.provider.ts` — реализация через REST API Gemini. Промпт живёт отдельно в `prompts/report.prompt.ts`.

**Требования к промпту:**

- Системная инструкция: отвечать **только** Markdown, без преамбулы, без обрамляющих тройных кавычек, без фраз вроде «вот ваш отчёт».
- Все числа — цены, километры, порядок объезда, вес — передаются во входных данных и **вставляются в отчёт как есть**. Модель их не пересчитывает и не округляет. Пересчёт моделью — прямой путь к расхождению между картой и отчётом, а это ловится жюри на первом же вопросе.
- Ответственность модели: формулировки, план размещения груза в прицепе с обоснованиями, замечания по совместимости грузов (продукты и стройматериалы в одном кузове, хрупкое сверху, скоропортящееся ближе к выходу).
- Структура разделов задаётся жёстко — та же, что в шаблоне заглушки. Так переключение между режимами не меняет вид отчёта.

**Обработка ответа:**

```ts
try {
  const text = extractText(response);
  const cleaned = text.replace(/^```(?:markdown)?\n?/, '').replace(/\n?```$/, '').trim();
  if (!cleaned) throw new Error('Empty LLM response');
  return { contentMd: cleaned, raw: response, source: 'gemini' };
} catch (error) {
  this.logger.warn(`LLM failed, falling back to template: ${error}`);
  return { contentMd: buildFallbackReport(summary), raw: null, source: 'mock' };
}
```

Модели любят обрамлять ответ тройными кавычками, даже когда их об этом прямо просят не делать. Зачистка обязательна — иначе на фронте вместо отчёта отрендерится один сплошной блок кода.

Таймаут на запрос — 15 секунд, не больше. На сцене никто не будет ждать дольше.

**Готово, когда:** с валидным ключом приходит отчёт от модели, без ключа — от шаблона, и внешне они различаются только формулировками.

### Блок 3 · Фабрика и диагностика — ~40 минут

`report.service.ts` — выбирает провайдера по правилам раздела 4 и делегирует ему вызов. Логика выбора в одном месте, не размазана по коду.

Добавь в модуль маленький диагностический эндпоинт — он не входит в демо, но экономит время при отладке:

```
GET /api/report/status → { provider: 'gemini' | 'mock', hasKey: boolean }
```

Согласуй путь с бэкендом-1 перед добавлением контроллера — это единственное место, где ты касаешься маршрутизации приложения.

**Готово, когда:** переключение `LLM_PROVIDER` в `.env` и рестарт меняют поведение, и `/api/report/status` это подтверждает.

## 6. Чек-лист готовности

- [ ] `generate()` не бросает исключений ни при каких входных данных
- [ ] Без `GEMINI_API_KEY` отчёт всё равно генерируется и он полный
- [ ] `LLM_PROVIDER=mock` не делает ни одного сетевого запроса
- [ ] Ответ модели зачищается от обрамляющих кавычек
- [ ] Числа в отчёте совпадают с числами в `Trip` — сверено вручную на одном рейсе
- [ ] Сумма цен в таблице отчёта равна итоговой стоимости рейса
- [ ] Таблицы отчёта корректно рендерятся на фронте
- [ ] Изменения не выходят за пределы `backend/src/report/`
- [ ] Переменные для `.env.example` переданы бэкенду-1

## 7. Если времени совсем мало

Приоритет жёсткий: **Блок 1 обязателен, остальное опционально.**

С одним первым блоком проект полностью рабочий и защищаемый — отчёт формируется детерминированно из реальных расчётов. Отсутствие Gemini на демо не заметит никто, а вот отсутствие отчёта заметят все.

Если успеваешь только Блок 1 — скажи команде сразу, чтобы на питче не обещали интеграцию, которой нет. Заявленная и не показанная функция стоит дороже, чем не заявленная.
